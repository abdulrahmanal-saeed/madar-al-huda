# FIQH-DEV-04 — review foundation

Migration version 3 adds reviewer profiles, explicit publisher grants, append-only revision review events, and a published revision pointer with database guards. Run only on a staging copy after versions 1 and 2 and the existing users table. No accounts, reviewer profiles, or approvals are seeded. Existing owners do not automatically become reviewers or publishers. Owner must explicitly verify a real reviewer and grant publisher permission. Human account is reloaded inside each transaction. Reviewer decisions record name, qualifications, user ID, time, notes, corrections and immutable hash. The assigned reviewer must decide; an editor of the latest revision cannot approve their own revision. Publishing requires the current approved revision and explicit publisher grant; the prior approved pointer stays intact when a new draft is saved. Incomplete issues and unverified source placeholders cannot pass the completeness gate.

This is backend foundation only. No admin actions or MCP actions invoke these methods yet, and no public feed reads the new pointer. The legacy fiqh publication behavior is unchanged and must be separately hardened before launch. Remaining: archive/withdraw workflow, qualification and permission changes audit, reviewer reassignment, full nested validation and edition model, safe public field projection (never expose actor/private notes), real authentication/CSRF integration, admin workflow controls, end-to-end tests. The database trigger checks matching latest approval, but authorization and completeness are enforced in the transactional service; it does not defend against a privileged SQL operator. Synthetic in-memory fixtures do not constitute real scholarly approval. No live migration or publish has occurred.

## Version 4 and admin integration
On staging only, run fiqhPermissionMigration after version 3. Permission changes now append immutable events. The authenticated admin route exposes explicit confirmed forms for review transitions, owner-only qualification profiles and grants, and publisher-only withdrawal of the exact published revision. Withdrawal removes the internal pointer but retains revision and decision history, including a newer draft. Dashboard counts distinguish latest review state from internal published pointers. The existing CSRF, session and action checks are used; backend rechecks permissions. The public feed is still disconnected. No legacy publish hardening, reviewer reassignment, full archival of never-published drafts, or production migration is included. Browser and end-to-end tests remain required.

## FIQH-DEV-08 structural hardening
All draft writes (including admin and MCP bulk import) now validate the supported nested schema before saving. Optional incomplete fields remain allowed in draft; unknown keys, malformed bilingual values, duplicate evidence IDs, invalid school/ID arrays and nested review injection are rejected. Per-issue maximum is 512 KiB and lists are bounded. Review rechecks the stored revision hash against its actual body and frozen sources, validates source records, and rejects approvals by anyone recorded as an author of any revision of the issue. The public projection uses the same gate. This deliberately restricts nested content to the current canonical contract; richer Quran/hadith locator objects, structured alternatives and terminology models are not yet supported and must be added explicitly, not silently discarded. Existing malformed staging drafts must be corrected before review. CI tests use synthetic content only. No production migration or activation.

## Review event concurrency
Every review transition now requires both the exact saved revision and the exact latest review event ID (0 only when no event exists). The admin form submits both; the transaction rejects stale decisions even when the same revision returns to the same state after a correction cycle. At publication the active reviewer's name and qualifications must also match the approval snapshot. This blocks a changed profile but does not constitute independent verification of a person's qualifications; revocation/reenablement or profile restoration with the same values is not a new approval. A changed profile that blocks publishing currently requires a new draft revision and review or restoration of the verified original profile. Tests cover stale approval and publication, and profile mismatch. No schema changes or production action. Applied exact Dart format correction from Commit 19 CI.
